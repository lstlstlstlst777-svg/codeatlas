# 与「agent 直接读代码」的对比

> 数据由 `scripts/intake_compare.py` 生成（`eval/intake_compare.json`），可重跑。
> 对比对象：Claude Code / Codex 这类"用 grep + read 自己翻代码"的 agent。

## 一句话

这不是"更聪明的 agent"，而是**一层可审计的检索**：
把"读哪些代码"从模型的多轮试探，变成一次可复现、可校验、成本与仓库规模无关的操作。

## 1. 信息摄入量（实测 8 个问题）

同一批问题，两种方式答完分别要读多少字符：

| 查询 | 本系统 | grep agent | 倍数 |
|---|---:|---:|---:|
| `zmalloc_used_memory` | 11,761 | 65,276 | 5.6× |
| how does Redis expire keys | 8,814 | 126,506 | 14.4× |
| where is the event loop created | 5,835 | 119,634 | 20.5× |
| list type push and pop | 5,704 | 127,459 | 22.3× |
| how to parse long long from string | 4,614 | 127,158 | 27.6× |
| acl user permission check | 5,223 | 139,065 | 26.6× |
| command table lookup by name | 3,787 | 128,433 | **33.9×** |
| replication handshake with master | 10,825 | 129,670 | 12.0× |
| **合计** | **56,563** | **963,201** | **17.0×** |

对 agent 的估算**刻意取最乐观值**：只读命中点上下 40 行，不读整文件、不做二次确认、
不算多轮累积。真实 agent 读得更多。

## 2. 结构性差别：成本是否随仓库增长

| | 本系统 | agent |
|---|---|---|
| 单次问答读入 | ≈ 7 KB（top-5 证据 + 题面） | 与命中数成正比 |
| 随仓库规模 | **不变**（只取决于 `top_k`） | 线性增长 |
| 随对话轮次 | 不变（每轮独立） | 累积重发，近似二次增长 |

Redis `src/` 是 5.88 MB / 约 **147 万 token**，任何 200k 上下文都装不下。
agent 必须"边翻边猜"，而每一次翻都要把之前读过的内容再发一遍。
本系统在 15 万行和 150 万行的仓库上成本一样——这是索引带来的解耦。

## 3. 可审计性：这是最本质的区别

| | 本系统 | agent |
|---|---|---|
| 引用 | 每条结论强制带 `path:行号-行号` | 通常不带，或带但无法校验 |
| 校验 | **三层机械校验**（区间存在 → 在本次证据内 → 文件 sha 一致，sha 不符标 stale） | 无，只能人工核对 |
| 实测 | **82/82 = 100% 通过** | — |
| 失败处理 | 校验不过 → 定向重写（注入允许区间清单），最多 2 次 | 无此机制 |
| 拒答 | τ 标定过的门（误拒 8%），答不了就明说 | 通常会硬答 |

agent 的答案你只能"读一遍觉得对"。本系统的答案可以**用程序验证**——
这是"看起来对"和"可审计"的区别，也是它能进生产的前提。

## 4. 确定性

- rerank 是确定性的（同输入跑 3 次完全一致，已实测）；
- 融合用应用层加权 RRF（k=60，1-based），不用 Qdrant 原生 RRF（k=2，0-based），保证可复现；
- 同一问题 + 同一索引 → 同样的排序与引用。

agent 每次探索路径不同，同一问题两次可能给出不同答案——调试和归因都更难。

## 5. agent 明确更强的地方（不回避）

1. **多跳推理**：问"这个函数被谁调用，调用链上哪一层加的锁"，需要沿调用图走。
   本系统只给 top-5 chunk，没有图结构，答不了。
2. **改代码 / 重构 / 写测试**：本系统只能回答，不能修改。
3. **全新语言**：切分器绑定 tree-sitter-c，换语言要扩 chunker；agent 不需要。
4. **模糊探索**："这块代码大概怎么组织的"——需要全局视野，检索给不了。
5. **精确字面命中**：`grep -w` 对标识符是 100% 精确的。本系统 Recall@1 只有 52%，
   靠"符号置顶"规则才把标识符类查询补上（见 ISSUE-025 的修复记录）。

## 6. 结论：互补，不是替代

正确用法是**把本系统当成 agent 的一个检索工具**：

```
agent 决定"要找什么"（多跳、追问、改代码）
   └→ 调本系统拿到 top-5 带行号的证据（可校验、成本恒定）
        └→ 基于证据生成，引用可机械验证
```

单独用 agent：灵活，但贵、不可复现、答案不可审计。
单独用本系统：便宜、可审计、确定性，但只能答"能在 5 段代码内说清"的问题。
