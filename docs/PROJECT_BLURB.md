## 一、简历版（推荐，直接粘贴）

**CodeAtlas — 带可校验引用的代码库问答系统**｜个人项目｜2026.10
技术栈：Python 3.11 / FastAPI / LangGraph / tree-sitter / BM25 + Qdrant 混合检索 / bge-m3 & bge-reranker / Redis / Docker

- **解决什么问题**：大模型答代码问题时常常"编引用"，结论无法核验。本系统要求每条结论都落到真实文件行号上，且能被程序机械校验，而不是靠人逐条核对。
- **结构感知切分**：基于 tree-sitter 解析 C 语法树，按函数/结构体/宏切分 Redis 7.2.5 源码（163 文件、7143 个语义块）。定位并修复 if-else 链导致的切分失效（单分支 1004 行切不动），超限片段由 42 个降至 2 个，最长片段 42250 → 14223 字符。
- **混合检索**：自研 BM25（标识符拆词 + 符号加权）与 bge-m3 向量检索并行召回，在应用层做加权 RRF(k=60) 融合后经 bge-reranker 重排；自建 40 条标注集评测，Recall@1 52% / Recall@5 72%。
- **引用可核验**：设计三层校验（区间存在 → 属于本轮证据 → 文件 sha 一致），失败时定向重写并注入"允许区间清单"，最多 2 次；实测 25 条问答共 **82/82 条引用 100% 通过校验**，零重写。
- **拒答而非硬答**：不拍脑袋设阈值，构造 25 条该答 + 15 条该拒的评测集，在 log₁₀(rerank_top1) 空间扫描阈值，以"误拒率 ≤10%"为约束最大化 F1，得到 τ=-1.00、F1 0.741、误拒率 8%；无证据时明确拒答，不产生幻觉。
- **工程化与性能**：增量索引按 file_sha 做文件级 diff（改 1 个文件只重嵌 3 个块，无变更时 5.08s 空转）；Redis 缓存向量与重排结果，同一提问检索段 661ms → **32ms**；SSE 流式 + 检查点实现断线恢复，恢复时不重跑检索。
- **多端接入**：同一套检索内核提供 Web 界面、HTTP API、MCP Server 三种接入方式；封装 `search_code` / `get_symbol` 接入 Codex，单次问答上下文读入约 7KB，较 grep+read 方式减少 **17 倍**。

**产出**：305 个自动化测试全通过、ruff 全绿；82/82 引用有效、命中目标符号 76.2%、端到端 p50 5.6s；Docker Compose 三容器一键启动；已开源 github.com/lstlstlstlst777-svg/codeatlas

## 二、极简版（版面紧张时用，3 条）

**CodeAtlas — 带可校验引用的代码库问答系统**｜个人项目
技术栈：Python / FastAPI / LangGraph / tree-sitter / BM25+向量混合检索 / Redis / Docker

- 用 tree-sitter 做 C 代码结构感知切分（7143 个语义块），实现 BM25 + bge-m3 向量混合检索与加权 RRF 融合重排，Recall@5 72%。
- 设计引用三层校验与定向重写机制，实测 82/82 条引用 100% 可核验；基于 40 条标注集标定拒答阈值，误拒率 8%，不确定时明确拒答而非编造。
- 增量索引 + Redis 缓存使检索段 661ms→32ms；支持 Web / HTTP API / MCP 三种接入，305 个测试全通过。

## 三、面试讲述版（口头/项目复盘）

**一句话**：把"大模型答代码问题"从"看起来对"变成"可被程序验证"。

**为什么做**：用 AI 读代码时最大的问题是无法判断它说的对不对——它给的 `file.c:120-140` 可能是编的。
RAG 方案常见做法是"把检索到的片段喂给模型"，但没人验证模型写出来的引用是否真的落在证据里。

**核心设计取舍**（这些是面试里最容易被追问的点）：

1. **为什么切分要用 AST 而不是按行滑窗**：C 代码的函数边界携带语义。滑窗会把一个函数劈成两半，检索到的片段缺签名，模型无法判断上下文。代价是要处理巨型函数（Redis 的 `rdbLoadObject` 1030 行），因此加了"语句边界兜底切分"——结构切不动时按语句起始行贪心切。
2. **为什么融合放在应用层**：Qdrant 自带 RRF，但它是 k=2、0-based，与业界常用的 k=60、1-based 不同源，评测结果无法与论文/他人复现。放在应用层虽然多几十毫秒，但换来可复现。
3. **为什么阈值必须标定**：rerank 分数跨 4 个数量级（相关 0.108 / 不相关 1.7e-05），线性尺度下任何阈值都会退化成"全过"或"全拒"，所以取 log₁₀ 后在标注集上扫。
4. **为什么要区分两种拒答**：评测时发现"被拒 4/25"，看起来拒答门太严；拆开看 4 条里有 3 条是**检索本来就没找到正确代码**——这时拒答是正确行为。混在一起统计会把检索问题算到阈值头上，优化方向就错了。
5. **为什么做 MCP 而不是只做网页**：网页是给人用的，MCP 是给 agent 用的。给 agent 只暴露检索（`search_code` / `get_symbol`），不暴露"帮我回答"——宿主本身就是 LLM，再过一层是重复劳动，且出错无法归因。

**踩过的最大的坑**：`split_oversized` 对 if-else 链完全失效。C 的 `else if` 在 AST 里是**嵌套**结构（else 分支里套下一个 if），按"直接子句"切永远只能切出一块。全量 70 个函数切了等于没切，包括 Redis 最核心的 `rdbLoadObject`/`debugCommand`/`clusterCommand`。这个问题不会报错，只会让检索质量悄悄变差。

**已知不足**（主动说出来，比被问出来好）：
- 评测集只有 40 条，置信区间宽，τ 需要更大样本重标；
- 只支持 C（切分器绑定 tree-sitter-c），换语言要扩 chunker；
- 索引绑定单一仓库，没有多仓库切换；
- 中文概念查询偶尔检索不到英文符号（"跳表插入" → `_quicklistInsert`），需要查询扩展。

## 四、注意事项

- 简历上**不要**写"Recall@1 52%"，写 **Recall@5 72%**。@1 是检索的第一条是否命中，对"给 5 条证据让模型自己判断"的场景意义不大；@5 才是实际使用的口径。
- "82/82 引用 100% 有效"是**引用格式与区间合法**，不等于"答案一定正确"。面试被追问时如实说明：它保证的是"引用不是编的"，答案质量由"引用命中 gold 符号 76.2%"衡量。
- 时间写 2026.10（当前月份）即可；如果要写起止时间，按你实际开发周期填。
